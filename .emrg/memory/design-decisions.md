## ① 部署形态 = 自托管 · 多用户（用户完全隔离，无团队）  `d4f0b8e1`

宿主原话：「自托管、多用户。目前不需要有实验室、团队的概念。每个注册用户都是独立用户。」

- 需要**后端服务 + 数据库**，可 `docker compose up` 自托管；有注册/登录/账号体系

- 已排除：纯前端 + IndexedDB（自带 Key）、公网 SaaS 多租户、实验室团队共用

## ② 转换管线 = 全自动 · 无人值守  `c5a9e3f7`

宿主原话（选 A）：「上传 → 解析 → 逐块翻译 → 产出可读中文文档，全程无人干预，失败只标记状态可重试。」

- 转换是**服务端任务**：任务队列 + worker + 状态机（`none/doing/done/failed` + 可重试）
- **取消人工验收环节** —— 现有 pku-paper-3d 流程里「宿主逐篇 `open` 浏览器验收才 commit」被产品化掉
  → **正确性必须内建在管线里**，不能靠人眼；仍允许人工**触发重试**
- 批量上传 + 前端转换队列进度（对应原型 `cv` 字段与导入抽屉）

## ③ 转换引擎 = 沿用 s_260803_0946_bf50 已验证的管线  `e8b4d2f6`

宿主原话：「会话 s_260803_0946_bf50 是怎么做的，这个效果我还是挺满意的。只是缺少英文 html 以及双向对比的过程。」

## ④ 双语配对 = 标记穿透翻译  `a2f7c910`

宿主亲自提出：「不是生成中文 html，而是生成英文 html，并给每个块添加标记。然后整篇翻译，翻译后的结果保留之前英文的标记，是不是就能对起来了？」

```
① PDF ──fitz──▶ 原文 + figures/ + 坐标
② 生成【英文 HTML】= 每块带稳定标记  <p data-b="b-0042">…</p>
③ 整篇翻译 ──▶【中文 HTML】，标记原样保留
④ 按标记 zip：b-0042 的 en ↔ zh 自动配对
```

- 配对**由构造保证**（无需事后段落对齐，避开中文精译合并/拆段导致的错位）
- 翻译仍**整篇**做 → 保住宿主满意的译文质量；块有稳定 ID → 顺带解决**段落笔记锚点 / 阅读进度 / 单块重译 / 三态切换**
- 产物仍为自包含 HTML（标记是 `data-` 属性，渲染不可见）
- **必须内建**：① **标记保真校验**（en/zh 标记集合相等、无缺失/重复、顺序一致、漏译检测 → 自动重译**该块**）② **块边界安全分块**（长文整篇一次翻译必被输出长度截断，须按标记边界切片，块不跨切片）

## ⑩ 分享 = 实时只读视图（**不是快照**）  `e5c4a8b1`

宿主原话：「分享链接不是快照。而是和分享者看到的是相同的页面，只是没有操作权限，无法上传、标识进度等。只能看。场景是：同学之间互相监督、互相学习、给导师汇报进度等等。」

- **原型实现（URL 内嵌 base64 快照 + `SHARE.active` 禁写）整个弃用** → 改为服务端承载的实时渲染
- **实时**：分享者更新后，访客刷新即见最新；**只读**：不能导入/改状态/改进度/编辑笔记
- 分享粒度 = **单个阅读计划**
- 与 ① 不冲突：隔离约束**写**，分享只放开**读**（且仅限被显式分享的计划）
- ⚠️ **版权风险**：公开链接将**无鉴权分发论文中文全文**，风险由部署者承担 → 需在 README/文档明确警示

**实现形态已纠正（2026-09-11，`00c6783`）**：第一版做成了「阅读器 + 文献下拉」的**独立精简页**（`.share-app` 独立 shell）→ 与「和分享者看到的是相同的页面」矛盾。原型答案在 `literature-workbench.html` L740–767：`body.readonly` 只是**隐藏写入类控件**（`#importBtn`/`#shareBtn`/`.ps-chev`/`#logoutBtn`/`.plan-new`/`[data-del-plan]`/`.note-form`/`#markRead`/`.nc-del`/`.side-user` 等全部 `display:none`），**外壳（侧栏+顶栏+五视图）原样保留**，顶栏下挂一条 `.share-banner`。现实现即此形态：`AppRoutes` 原样挂在 `/share/<token>/*` 前缀下，前端统一用 `useReadonly()` 分支（不写死 `/share/...` 路径 —— 有样式护栏拦截）；后端 `readonly_share_guard` 中间件对带 token 的非 GET 一律 403。

## ⑪ 分享访问控制 = 持链接即可匿名只读 + 可撤销/有效期（不做密码）  `b8e2f4a6`

宿主回答：「A+D」「A 起步 + D 的撤销/有效期（不做密码，避免又要传密码）」。

- **A**：持有链接即可访问，无需登录；链接本身即凭证（长随机 token，不可猜）
- **D**：可随时**撤销** + 可设**有效期**；**不做访问密码**
- 推论已确认：分享场景含**给导师汇报** → 导师不会注册 → **匿名读路径是必需项**，纯「必须登录」不可行
- 实现须内建：token 不可枚举；撤销/过期**服务端立即失效**；只读须**后端校验**（不只靠前端隐藏）；失效后返回明确提示

**⚠️ 有效期上限 = 24 小时（2026-09-11 宿主指示，㉔）**：「分享链接有效期最大设置 24 小时」。
- 单位从「天」改「小时」：`expires_in(hours)`，钳制上限 `SHARE_MAX_HOURS=24`（`server/config.py`）。
  **永久链接这条路整体取消**（旧版 `days=0 → expires_at=NULL` 已不可能产生）。
- 上限钳制放在 **`expires_in` 里**而不是路由层：任何入口（旧客户端 / curl / 重放请求）都逃不掉。
  超限不报错、**直接钳到 24** —— 这类约束的失败方向必须是「更短」，不能是「更长」。
- 存量永久链接由启动迁移 `_migrate()` 收敛为「从现在起 24h」（**不直接作废**：已发出的链接立刻全废，
  访客看到的是"链接坏了"而非"过期了"）。
- 配置项 `PAPERSHELF_SHARE_DAYS` → **`PAPERSHELF_SHARE_HOURS`**（默认 24）。
- 前端下拉 = 1 / 6 / 12 / 24 小时；到期显示改**小时精度**（只显示到「日」两条链接会看起来一样）。

    经 `GET /api/auth/config` 下发，前端 `<details>` 渲染全文 —— **前端不复制文案**（防两边漂移）。

    → 所以这句写成**用户的承诺**，而不是软件保证的能力。

| 路径 | 行为 |
|---|---|

| **贴 arXiv 链接 / ID**（如 `arXiv:1706.03762` 或 `arxiv.org/abs/…`） | 服务端**优先抓官方 HTML 版** `arxiv.org/html/<ID>v<N>`；**无 HTML 版则回落到下载 PDF** |

2. **LaTeX 未损坏**：`<math alttext="…">` 属性直接给出干净 LaTeX，比 PDF 文本提取准确
3. **绕开 PDF 截断链**：PDF 被代理静默截断后 XObject 流损坏 → MuPDF/PDFium/sips **全部渲染失败**；走 HTML 直接规避

### 与 ③④ 的协同（实现要点）
- arXiv 官方 HTML 已具**语义块结构**，可作为**英文 HTML 结构**的现成素材来源 → 有利于决策④ 的「带标记英文 HTML」生成
- 但**标记方案仍由 papershelf 自己定义**（arXiv HTML 只是素材，不是最终产物）
- 非 arXiv 论文一律走 PDF 路径，用既有 fitz 流程

- **PDF 下载完整性校验**：比对 `content-length` + PIL 检测底部 25% 纯黑占比 >50% 判截断；补全用 `curl -sL -C -` 多轮续传

- 表格**坐标级重建**（`get_text()` 会打乱行内单元格顺序，须用 line 级 `x0` 判列）

## ㉗ 转换任务队列 = 常驻队列 + 启动恢复 + 原子认领（2026-09-12 事故修复）  `b7f3e9a4`

宿主原话：「为什么我生产上文献库，只有一个已生成，其他都没有继续转化」

### 病因（三件事叠加，缺一不可）

1. **任务挂在 HTTP 请求的 `BackgroundTasks` 里**：上传播时用 `BackgroundTasks` 起转换
   → 只有"那次请求"知道任务存在。
2. **并发上限 2，其余在请求线程里干等**：抢不到信号量的论文不是"排队"，是**各自占着一个
   请求线程阻塞**——请求不结束，连接和线程都不释放。
3. **无启动恢复 + 无 DB 轮询 worker**：容器 22:41 被重启（`Container papershelf Recreated`）
   → 杀掉 2 篇跑到一半的，永久停在 `doing`（僵尸）；9 篇 `queued` 是**孤儿状态**——
   `queued` 只是 DB 里一个字符串，真正跑任务的是那次 HTTP 请求里的 `BackgroundTasks`，
   请求结束就没人再看它。**§5.6 写的「DB 轮询 worker」从未实现**，UI 也不给
   `queued`/`doing` 重试按钮（只对 `failed`/`none` 给）。

### 确定（宿主选 A：治本）

1. **常驻队列**：`server/queue.py` 的 `ConversionQueue` 在 `lifespan` 启动，按
   `PAPERSHELF_QUEUE_INTERVAL` 轮询 `papers.conv_state='queued'`，**不依赖任何 HTTP 请求**。
2. **启动恢复**：启动时 `recover_stuck(conn)` 把 `doing` 一律复位为 `queued`
   （上个进程被杀留下的僵尸）→ 队列随即捡起。⚠️ 未引入"心跳/租约"：单进程部署下
   "进程活着 ⇒ 没人在 doing 半途" 成立，加租约只是复杂度。
3. **并发 = 常驻工作线程池**：`_Pool`（`max_concurrency` 个常驻线程，`Queue(maxsize=并发数)`）
   → **同时交付** N 篇。⚠️ 早先用"轮询里逐个跑"是**串行**的，实测发现后改的。
4. **原子认领**：`claim_paper(conn, paper_id)` 用 `UPDATE … SET conv_state='doing'
   WHERE id=? AND conv_state='queued'`，**行数=1 才算认领成功**——这是全局唯一的互斥点。
5. **顺序铁律：先抢槽位，再认领**。`convert_paper` 必须
   `with concurrency_semaphore():` **之内**才 `claim_paper`。反过来写（先认领后抢槽位）在
   并发 2、队列 8 时**瞬间把 8 篇全变 doing**，界面显示 6 篇假「转换中」——**正是本事故的
   另一种版本**。已加护栏测试钉住。
6. **信号量惰性求值**：`concurrency_semaphore()` 是函数，不是模块级
   `_sem = threading.Semaphore(...)`。后者在**导入时**求值，改环境变量/测试夹具都不生效。
7. **前端忙时轮询**：`planContext` 仅在 `busyCount > 0`（有 `queued`/`doing`）时每 4s
   `reload()`，安静后**自动停**（防无脑轮询）。护栏测试要求这个门控存在。
8. **测试夹具默认关掉常驻 worker**（`conftest.py` 改环境变量）：否则现有测试会被后台线程
   二次处理，结果不确定。

### 实测验收（真 LLM，本地 `/tmp/psq`）

- **重启恢复**：`kill -9` 精确复现事故（2 doing + 1 queued）→ 重启打印
  「启动恢复：2 篇卡在 doing（上个进程被杀）→ 重新排队」→ 队列并发捡起 → **全部 3 篇 `done`**。

  `_finalize` 把**全部 h1 候选**存进 `meta["title_candidates"]`（不再销毁），
  并在 prompt 里明说「**第一个往往是期刊名**，请挑真正的论文标题」。
- **输出强校验，失败退回不写**：去 markdown 围栏、抠第一个平衡 `{...}`、
  `year` 必须落进 1900–2100 的 int（`papers.year` 是 INTEGER，喂字符串会静默变 0）、
  `tags` 归一（中文分隔符、去 `#`、去重、上限 5）。**宁可不写，不能写错** ——
  写进去的垃圾会被下一层的"不覆盖"逻辑锁死。
- **抽取失败绝不打挂整篇**：元数据是锦上添花，译文才是主产物 → 异常吞掉返回 `{}`。

### ⚠️ 占位标题：必须落列，不能现场推导（同日踩的第二个坑）

第一版判据是「`title == Path(pdf_path).stem`」—— 看着干净（用户一改就不相等，自动获保护，
连迁移都不用）。**实测生产 12 篇全部判成"非占位"**：

```
title    = 'original'
pdf_path = '/data/papers/2026-09-11T143352+0000_original.pdf'   ← 落盘加了时间戳前缀
Path(...).stem = '2026-09-11T143352+0000_original'              ← 永不等于 title
```

即"修好"之后真标题**仍然写不进去**，只是从"必错"变成"看起来对"。
→ **教训：占位符是一种意图，不是一种值。** 需要"当时那个文件名"的信息，
事后从被改过的路径里**推不出来**，只能落列：

- 新增 `papers.title_is_placeholder`（导入时 1，用户 PATCH 改标题时 0）；
- 判据**单一来源** `server/titlemeta.py`：`converter` 与 `db._migrate` 共用一份
  （放 `converter` 会与 `db` 成环）；缺列时退回路径兜底，**先比 `source_ref`
  （原始文件名）再比 `pdf_path`** —— 实测生产 12 篇靠 `source_ref` 全部认回占位。
- 迁移做存量回溯，认不出的一律保持 0（**不覆盖**）：宁可让用户手点一次，
  也不能擅自吃掉他可能手填的标题。

### 写回优先级（用户手填 > 自动抽取）

`title`（仅当占位）· `authors`/`venue`/`year`/`tags`（仅当为空）。
`PATCH` 顺手把 `title_is_placeholder` 置 0 —— 否则用户填的标题会被下次转换顶掉。
另修 `PATCH` 的 `body.x is not None` → `model_fields_set`：
旧写法分不清「没传」与「显式传 null 清空」，抽屉里清空年份会"保存成功但清不掉"。

### 实测数据（真 LLM，生产真实 PDF）

对 4 篇"标题取错/为空"的跑抽取：**4/4 修好**（第 1、3 篇正确挑中**第 2 个候选**，
第 7、6 篇恢复了解析器从没捕获到的真标题），合计 **5,930 tokens ≈ 1.5k/篇**。
→ **回填 12 篇 ≈ 1.8 万 tokens，而"重跑转换"要 185 万 —— 便宜约 100 倍。**

### 存量回填工具

`papershelf backfill-meta [--dry-run] [--limit N] [--only-missing/--all]`：
复用已有解析产物（块已在库），只跑抽取并按同一套优先级写回。
**⚠️ 做这个工具时踩到一个诊断缺陷**：`log=lambda *a: None` 把 LLM 的连接超时整段吞掉，
输出只剩一行 `→ (无) | — | — | — | []`，看上去像"模型没抽到东西"，实则**一次都没连上**，
且每篇都等满 300s（12 篇 = 一小时）。现在如实打失败原因，并做**短超时连通性预检**
（`--probe-timeout`）—— 端点不通就中止且不落任何修改。

**⚠️ 第二个坑（生产 dry-run 才现形）：存量文献抽不到标题。**
3 篇的 `authors`/`venue`/`year`/`tags` 全抽到，但 `title_zh`/`title_en` **全空**。
原因：这些文献是被**旧版** `_finalize` 处理的 —— 它取第一个 h1 当标题后把**其余 h1 全删**，
而那些 h1 **没存进 meta**（`title_candidates` 是随本次修复才有的）。
于是存量块里**根本没有标题文本**，模型按 prompt 要求如实返回空串。
→ 修法：候选标题**优先用存量 meta，没有就重解析 PDF 现场取**（只吃 CPU、不花 token，
与转换路径同一个 `parse_pdf`；只对"存量无候选且 pdf 还在"的行做）。
实测：不给候选 → `None`；给候选 → 正确中文标题。

### 生产回填结果（2026-09-12，`sha-49230d0`）

**12 篇全部回填成功，合计 19,181 tokens（≈1,598/篇）** —— 与预估的 1.5k/篇吻合，
相当于重跑转换（1,855,352）的 **1.03%**。12 篇中文标题/作者/期刊/年份/标签全都有了
（仅 #1 的 year 为空，模型如实说判不出来 —— 符合"宁可留空不编造"）。
生产 UI 实测：12 行全部显示真标题 + 作者 + 发表 + 标签，`t-del`/`t-edit` 各 12 个，零 4xx。

### 修订（2026-09-13，宿主定口径：**回填成功 = 已确认**）  `f1c2a907`

**症状**：回填完成后，生产 12 篇的 `title_is_placeholder` **仍是 1** —— 标题是真的，
标记却说"这还是占位值"，**列在说谎**。两个真实代价：

1. `backfill-meta --only-missing` 的判据是「标记为 1 **且** 没作者」→ 这 12 篇每跑一次
   都会被当成"仍缺元数据"**重抽一遍**（≈1.6k tokens/篇，白烧 —— 正是"回填"这一整套
   为省钱才存在，结果自己成了漏钱口）。
2. 用户看到的"已回填"与系统认为的"仍待回填"是两回事，界面上一眼分不出。

**根因**：`_writeback_meta` 写回了抽到的真标题，**却没同步撤标记** —— 而这一列的名字
就是它的语义（"标题还是导入时那个文件名"）。同一件事在**两端**各需要一个动作，
只做了一端的必然结局就是列在说谎。

**修法**：写进抽到的真标题时**同时**置 `title_is_placeholder=0`（`converter._writeback_meta`）。
**代价（刻意接受）**：重跑转换**不再覆盖已抽出的标题** —— 保护范围从"用户手填"扩到"已确认"。
抽到的标题就当这篇的定稿，要改就手工改，与用户手填走同一条路。
**反向约束**：抽取失败（`{}`，没拿到标题）时标记**必须留在 1**，否则这篇永远补不上 —— 已加断言钉住。

**存量 12 篇**：一次性数据订正（判据刻意保守：`papers.title` 非空**且等于该篇 `docs.meta`
里的 `title_zh`/`title_en`**，即"能证明这个标题是抽取写进去的"才撤；这样 arXiv 占位
`arXiv:2603.19455`（路径推导不出来）不会被误判）。订正前备份 `papershelf.db.bak.20260913-1054-flagfix`，
订正后 `flag=1` 归零、标题 12 篇原样。
**验收**：容器内 `backfill-meta --only-missing --dry-run` → **「本次处理 0 篇」**
（此前 12 篇），即"再也不会重复花钱"从一个判断变成了一条可复现的观测。

## ㉛ 划痕 = 任意字符区间 + 四支不带含义的笔（2026-09-13 宿主指示；**推翻 ㉚ 的②③④**，保留①）  `f1a4c7e3`

> **同日修订（`350f33f`）**：拖选收尾那一下 `click` 会把 `mouseup` 刚点亮的浮条当场收掉
> → 「浮条一闪即没」，主路径不可用。见文末「㉛ 修订」。

**起因**（宿主原话）：「现在是点击一句话后，选择高亮。这**不是标准阅读论文时高亮标注的方式**。
标准高亮时，是**选择一个颜色的笔，随意高亮选中的部分，不一定是整个句子**。
并且可以**选中任意部分后添加备注（笔记）**。」→ 追问颜色语义，宿主答「**好看的几种颜色、没有含义**」；
问「要不要先在原型里定格交互形态」，宿主答「**你定**」→ 助手定形态并**同步写进原型**。

### 核心：锚点从「句」换成「字符区间」

`(block_id, lang, start, end)` —— 块**裸文本**（`blocks.en` / `blocks.zh`）的字符偏移，闭开区间。

- **尺子由服务端给**（`pipeline/markup.prose_html`）：在文本单元的**每个端点**吐零宽锚点
  `<span class="o" data-o="N">`。前端按文档序走一遍文本节点累加字符数、
  **遇到锚点就把计数「拨」到 N**（不是加），遇到 `<math>` 整棵跳过 →
  "屏幕上划的那几个字"才能变成可持久化的数字（`web/src/marks.ts`，5917 字符，前端唯一懂裸文本偏移的地方）。
- ⚠️ **锚点不能省，也不能只在公式两侧放**：每个单元两端都要有，否则两次公式之间的那段文本没有起点可数。
  但 `anchors` 默认 **False** —— 只有"要交给用户去划线"的视图（阅读器 / 分享页）才开。
  翻译 prompt、校验产物（`synth.py`）、导出文件都吃这份 HTML，多一层空 span 只会让产物更难 diff、
  让 prompt 更贵。**与 `typeset` 同一取向：不发锚点最多是"划不了新的一道"，发错地方是往 LLM 输入里掺垃圾。**
- **公式是原子**：`\(x\)` 在服务端变成一整棵 `<math>` 子树（里面也有文本节点，但那是**排版产物**，
  与裸文本字符不对应）。前端光标落进公式内部 → **吸附到它的两端**；服务端侧与划痕相交的公式
  **整个**被包进 `<mark>`（宁可多包一点，也不能把 MathML 从中间劈开）。
  两条规则互为兜底 → 界面上永远不会出现"半个公式"。
- ⚠️ `_MATH_RE` 必须与 `mathml.render_math` 的**分段正则逐字一致** —— 它决定"渲染后哪些字符不再是文本"，
  不一致的后果极隐蔽：前端算出的偏移会与渲染结果错位几个字符，划痕整体平移。

### 数据模型（`highlights` 表重做）

`id, paper_id, block_id, lang, start, end, color, created_at`（旧表是 `(paper_id, sid)` PRIMARY KEY）。
**仍然不存文本** —— 文本永远从服务端渲染的块 HTML 里取，重跑管线后区间仍在，划痕跟着新译文走。

**旧数据迁移**（`db._migrate_highlights_to_ranges`，启动时）：检测旧表有 `sid` 列 →
`SELECT` → `DROP` → 按新 DDL 重建 → `_resolve_sid_span()` 用 `_SID_RE = ^(.+):([ce])(\d+)$`
解出块 id / 语言 / 句序 → **重跑切句**（`markup.sentence_offsets`）确定性换算成区间 → 插回；
换算不出来的行 `dropped += 1`（**不静默丢**）。
⇒ `split_en` / `split_zh` **保留下来并被测试钉住**，不做"顺手优化"：它们一变，存量换算就整体错位。

### 交互形态（助手定，已同步进原型）

- **四支笔** `amber / green / blue / pink`，**完全等价**：不做图例、不做语义编码
  （"黄=重点"会让用户担心"颜色用错了"）。也**不受**原型那条「status palette — data encoding only,
  never decoration」约束 —— 那条只管状态色（待读/在读/已读）。
- **两条落笔路径都通**：① 工具栏先选笔（记忆在 `localStorage`）→ 拖选 → 浮条上点颜色；
  ② 直接拖选 → 浮条上点颜色。划完浮条留在原地，接着点「加笔记」时笔记就锚在这道划痕上。
- **浮条 / 就地菜单是同一个组件的两种形态**（`.mark-bar`，`position: fixed` 到**视口**坐标）：
  `kind:'sel'`（刚拖选）与 `kind:'mark'`（点已有划痕，多一个「擦掉」）。
- **点已有划痕 → 就地小菜单**：换笔 / 加笔记 / **擦掉**。
- **擦掉 ≠ 删批注**：`repo.delete_highlight` 只把笔记的 `hl_id` 置 NULL ——
  笔记有自己的坐标（`block_id/lang/start/end`），划痕只是视觉上的兄弟。
  擦掉荧光笔却把批注一起删掉，用户会认为是丢数据。
- **跨段选区内部拆开**：坐标是**每块每语言一份**裸文本的偏移，块与块之间没有共同坐标系 ——
  跨段划痕在数据模型里本来就是好几道。界面同色连成一片看不出区别，但"擦掉"只擦你点中的那一段（可接受）。
- **落笔后只重画受影响的那几块**（`GET /api/docs/{pid}/blocks/{bid}` → 整块替换）。
  为什么不前端自己包 `<mark>`：那是**第二份排版实现**，公式/转义/跨行都要各写一遍，立刻与服务端分叉。
  为什么不重拉整篇：900 块的文档几百 KB，划一道重下一次纯浪费。
- **笔记文案**：`anchorLabel` 写「第 N 段（中文）· 第 a–b 字」（1 起、闭区间）。
  段号是**正文段**计数而非块序号 —— 块序号里混着标题/图表/公式，直接用会出现"第 137 段"这种对人不友好的数字。
  卡片圆点带 `pen-<色>`，与色板**共用一份颜色定义**，圆点才不会与原文底色说两套话。
- **点笔记 → 跳到那道划痕**（`[data-h]`）+ `.is-flash` 1.4s，卡片 `.is-on`。
  **两级落点**：划痕不可见（被擦掉 / 当前语言模式下隐藏）时退到整块（`data-b`）。
- **只读分享态能看不能改**：颜色看得见、卡片在；色板 / 浮条 / `nc-del` / 笔记表单全不渲染。
  写路由由后端 403 兜底（⑪）。

### 前端两条硬约束（M3 起就有，㉛ 再次踩到）

1. **块 HTML 由服务端给** —— 前端不排版公式、不自己把选区包成 `<mark>`；

### ㉛ 修订：拖选后浮条一闪即没（2026-09-13，`350f33f`）

**症状**：真人在浏览器里拖选文字 → 浮条**闪一下就没**（划过重点这条主路径整个不可用）。

**病灶**：拖选结束时浏览器**还会补一个 `click`**（target = 落点所在块），而"点别处 = 收浮条"
挂在 `click` 上（`ReaderPage.stageClick` 的兜底分支）→ `mouseup` 刚 `setBar(...)` 的浮条
被紧跟的 `click` 当场 `setBar(null)`。
**原型没有这个缺陷**：它把收浮条挂在 `stage.mousedown → hideBar()`，
而 mousedown 发生在**选区形成之前**，天然躲开这个顺序问题 —— app 从 mousedown 挪到了 click
（顺带承担"点空白块 → 选中该块"），就必须自己认出"这一下是拖选的尾巴"。
判据：`window.getSelection()` **非塌缩** ⇒ 是拖选尾巴 ⇒ 只更新 `selBlock`，**不动 bar/target**。
（原型侧同日补了注释说明为何必须挂 mousedown，文件：`/Users/argszero/Downloads/t1/literature-workbench.html`。）

**为什么上一轮"真浏览器实测全绿"仍然漏了**：那些用例是**合成事件**（`dispatchEvent(new MouseEvent(...))`
/ `el.click()`）驱动的，而合成事件**跳过**了浏览器真实的事件序列 —— 缺陷恰恰长在
`mouseup → click` 这个**衔接**上。改用真实鼠标事件（CDP `Input.dispatchMouseEvent`）后，
连 MutationObserver 都能拍到 `+DIV.mark-bar` 紧接着被移除。
**方法论（写给下次）**：
1. **"能跑通"与"点了会有反应"是两件事** —— 合成事件证明的是"处理函数没写错"，
   证明不了"真实序列下状态还在"；凡涉及 `mousedown/mouseup/click` 顺序的交互，
   验收必须走真实输入事件。
2. 排查这类"一闪即没"用 **MutationObserver 记 DOM 增删**（比轮询快照可靠）——
   能直接看出"加过又删了"，而不是"压根没加"。
3. **本地/生产都要跑一遍**：本地 8012 已复现，说明这不是环境差异，别把它当"生产才有"。
4. 若要在浏览器里驱动真实点击，**必须先 `activate_tab(current_tab())`** ——
   后台标签页收不到 CDP `Input.dispatchMouseEvent`（表现为"事件全丢、日志为空"，
   与"处理函数没挂上"长得一模一样，极易误判）。

## ㉜ 阅读顺序 = 分区处理 + 栏间空白剖面（2026-09-14 宿主报「pdf 抽取原文不对」）  `a2c8f4e1`

**宿主原话**：「pdf 抽取原文不对」+ 截图（生产 `/reader/12`）。表现：**正文首句没有开头** ——
`1 Introduction` 下面第一段是「unattainable concepts in smart materials (SMs) [7] …」，
而它其实是**右栏第二段的续写**；真正的首段「AM, also known as 3D printing…」被排到了它后面。

复现论文 = 生产 paper 12 = `B7-01-AI-in-AM-review`（宿主给的本地 PDF 是该篇；他第一次说的
`B3-01-ML-in-AM-review` 是另一篇，第一篇能解析正常，据此定位到真正病灶）。

### 根因
旧 `_reading_order` 把整页**二选一**地判成「单栏 / 双栏」，判据 `_two_column` = 左右各 ≥4 个窄块。
而该页是**混合版式**：通栏的页眉/标题/作者/摘要 + 下方**双栏正文**（左栏首段 + 右栏续写两段）。
整页一刀切的启发式判成**单栏**（实测 left=9 / right=3，不到阈值 4）→ 退回"按 y 排序"
→ **两栏逐行交错**，右栏段落在左栏段落之间来回穿插。

**这类缺陷的性质**：不是崩溃、不是报错，而是**静默把句子拦腰接错**，产出"读得通但读不通"的译文——
比任何异常都难发现（校验器只查标记保真，不查人能不能读懂）。

### 修法（`_reading_order` 改为分区）
1. 按 y 把块切成「**通栏段 / 窄块段**」（宽度 > 页面 62% 视为通栏）；
2. 通栏段按 y 排；窄块段再尝试**分栏**，成功则「左栏整栏 → 右栏整栏」；
3. 分栏判据从"左右各 ≥4 个窄块"换成**覆盖度剖面**找栏间空白(gutter)：
   在页面中央带（0.35–0.65）逐点统计"有多少块横跨这个 x"，取最小值处切栏
   （真栏内任意 x 都被大量块覆盖，只有 gutter 接近 0）。

### 为什么不用「相邻块间隙 ≥ N」（两条实测反例，缺一不可）
- **公式会溢出栏间**：B5-01 第 7 页右栏自 `x=300.9` 起，左栏一道公式的 `≤ 0` 伸到 `299.2`
  → 真空白只剩 **1.7pt**，任何像样的间隙阈值都扫不出来（实测那页 55 个块被判成"一栏"）；
- **页码常卡在栏间**：B2-03 第 24 页的页码 `186` 正落在 `x=292.6..305.3` 的空白里
  → 相邻扫描会被它"桥接"。所以找 gutter 必须**只看正文带**（排除页眉/页脚/页码）。

### `PARSE_VERSION` 2 → 3 → 4 → 5
阅读顺序是**解析产物的一部分**。不升版本号 → `doc_cache`（主键 = PDF sha256）**永远命中旧解析**，
修复看起来"完全没生效"（这是同一个坑第二次：分页那次也是这样，见 ㉔）。
- **3**：阅读顺序（多栏/通栏分区）
- **4**：分栏重写（`_body_size` 字符数加权中位数 / `_marginal` / `_gutter` 覆盖度剖面；
  实测 265 页：变好 62 / 变差 0 / 持平 203）
- **5**：抽取文本**确定性清洗**（连字 `ﬁ`/`ﬂ` → `fi`/`fl`、`\xa0` → 空格，`clean_text`）

### 实测（本机 12 篇真实 PDF / 265 页，逐页对比旧实现）
- 修复 **35 页**、同 **217 页**、顺序变化 **13 页**
- 13 页里 **12 页是表格**（旋转表/多列表，按栏读本就不适用，旧新两种顺序都不可读）
- 剩 1 页是 arXiv 公式密集页，两种顺序都不可读 → **无真实回归**
- 目标页 B7-01 首页：`1 Introduction` → 左栏首段 → 右栏续写 ✓
- 两条反例页（B5-01 p7 公式溢出 / B2-03 p24 页码卡栏间）均分栏成功 ✓

离线回归 **201 项**（新增 `tests/test_parse_order.py` 7 项，全部合成 bbox、不读真实 PDF；
已用"复刻旧算法"反向验证新用例在旧实现下确实红，避免写出永远通过的空测试）。

### ⚠️ 遗留：存量文献需要**重跑管线**才能吃到修复
解析结果已落库（`blocks` 表），修复只影响**新解析**。`save_doc` 是**整篇 DELETE + 重插**，

## ㉝ 原文校对 = LLM **agent**（新增管线 ①c）（2026-09-14 宿主指示）  `c5e0b8a3`

**宿主原话**（先后两段，第二段定形态）：

1. 「LLM 需要用于提取后的校对更新，要校对文字、格式，**所有能校对的都要校对**」
2. 「参考 emrg 代码，在提取完成后，llm 校对更新的方式应该是 **agent 方式**的，也就是给 agent 提供
   输入（原始 pdf 或者 pdf 转成的图片、提取的结果），以及工具（读图片工具、读提取结果的工具、
   **修改提取结果的工具**等等）。然后让 llm 以 agent 的形式来校对更新。」

### 形态（对齐 emrg 的 tool loop，`pipeline/proofread.py`）

| 环节 | 内容 |
| --- | --- |
| 输入 | **原始 PDF**（渲染成页图，可 `region` 放大）+ **抽取结果**（块 id/类型/文本/bbox/页号） |
| 读工具 | `read_page(page[, region])`、`read_blocks(page[, offset])`、`read_block(id)`、`check_artifacts(page)` |
| 改工具 | `edit_block`、`split_block`、`merge_block`、`delete_block`、`reorder_page` |
| 收尾 | `mark_page_done(page)`、`finish(summary)` |
| 循环 | `finish_reason == tool_calls` → 执行 → 每条一条 `tool` 消息 → 继续（仿 emrg `_run_tool_loop`） |
| 位置 | ① 解析 → **①c 原文校对（agent）** → ② 公式 LaTeX 化 → ③ 翻译（校对必须在翻译之前：改的是**英文块**） |

⚠️ **图只能跟在"全部 tool 结果"之后**（一条 user 消息带 image_url）：插在 tool 消息中间会破坏
`tool_calls` ↔ `tool` 的配对，provider 直接报错。

### 决策要点

- **只改"看出来的错"**；文本必须逐字来自论文，不许润色/补写。
- **护栏**（`_acceptable_text_change`）：不许暴涨（>3 倍 + 300 字符）、不许太不像（相似度 <0.55）——
  模型会编，护栏是**执行层**的兜底，不是提示词里的请求。
- **漏页不算完成**：还有页没 `mark_page_done` 时 `finish` 被拒并点名；页级续跑
  （`doc.meta["proofread"]["ok_pages"]`，重跑只补没校过的页，不重复计费）。
- **抽取丢失**（图里的图标/编号/表格结构）只写进笔记，**不凭想象补写**到文本里。
- 与 **⑯ 不冲突**：⑯ 否掉的是"**译文**语义自检（回译/VLM 比对）"，这里是**原文抽取**校对，
  对象与目的都不同（⑯ 的结论仍然有效）。

### 成本（★ 这一节全是实测，不是估）

**病灶**：池子里可用的视觉模型（`deepseek-v4-flash-vision-exp`）是**推理模型**，
而同一条请求的 `completion` 几乎全花在思考上：

| 参数 | completion tokens | 用时（同一条请求） |
| --- | --- | --- |
| 默认（auto） | 2001 | 10.0s |
| `max_tokens=1500` | 1179 | 8.6s |
| `reasoning_effort="low"` | 1179 | 6.3s |
| `reasoning_effort="minimal"` | 693 | 3.7s |
| `thinking={"type":"disabled"}` | **80** | 1.1s |

**3 页小样本**（同一篇真论文，产出同样 12 处修订）：auto **16 轮 / 106,709 tokens** →
`off` **13 轮 / 81,369** → `minimal` **8 轮 / 60,665**。
→ **成本 ≈ 轮数 × 每轮输出**，而每轮还要重发一遍上下文，所以"轮数"是唯一的大杠杆。

**37 页真论文（503 块）端到端**：`minimal` 时 **33 页 / 78 轮 / 459 次工具 / 899,373 tokens /
715s**，共 170 处文字修订（断词合并 + 引用编号空格为主）→ **≈27k tokens/页、≈12 分钟/篇**。
（对照：整篇翻译约 15 万 tokens/篇 → 校对约为翻译的 6 倍。这是"逐页看原图"这个形态的固有代价，
宿主明确要的就是这个形态；要更省只能减少页数或页图分辨率，会直接伤到校对质量。）
→ 默认 `proofread_token_budget = 1.5M` 够一篇 37 页跑完，但余量不大（另一篇更长的要留意）。

三条压制措施（缺一不可）：

1. **`PAPERSHELF_PROOFREAD_THINKING`，默认 `minimal`**（`off` 质量崩、`auto` 最贵）；
2. **seed 里只放页级可疑计数**（`_suspect_pages`，纯字符串计算、零成本）→ 省掉探索轮次；
   明细下移到当页工具结果（`read_blocks` 的 `flags` / `check_artifacts`），详见 ㉝ 补记；
3. **提示词写"每页两轮" + 硬护栏**（连续 3 轮没有 `mark_page_done` 就追问一次）——
   *提示词不是护栏*，实测模型会一轮一个改动地磨。

### ⚠️ 长任务的两条铁律（2026-09-14 真跑 37 页时被咬出来的）

**① 瞬时故障必须重试。** 上游网关对超大请求约 **60s 就 504**（实测三次 504 都隔 64s 返回）。
第一版里 `retries` 参数是个**从未被使用的摆设** → 一次 504 让"跑到第 11 分钟、已改 173 块"的
整篇校对**归零**。现在 `_post` 对 `429/5xx/超时/断连` 退避重试（2s/4s/8s…），
`4xx`（除 413）立即抛——**重试不会救请求本身写错的情况，只会白花钱**。

**② 中断必须交账。** 重试用尽也不能把成果扔掉：`proofread_doc` 兜住异常、把
`stopped = 中断（…）` 记进统计，`ok_pages` 照常落库。实测第二次跑到 504 时，
**33 页的成果全部保住**，只报"还剩 34–37 页"。配套修掉一处真缺陷：
converter 原先的判据是"**有页校过就整篇跳过**" → 半成品会**永远**停在那里、
界面还显示"已完成"；改成 `_pending_proofread_pages()`（有块的页 − 已校页 = 还要校的页，
空集才跳过）。

### 踩坑（都会静默毁掉整篇，务必保留）

- **请求体上限 = 1MB**（实测 1MB 过、1.5MB → 413），且 413 回的是 **HTML 错误页**，
  `resp.json()` 会炸掉整篇 → 加体积闸门（按体积剪最旧的图）+ 413 兜底重试。
- **推理模型 `max_tokens` 给小 → 全烧思考、`content` 返回空串**（实测 8192 必空）。
- **切分时新块 ID 重复**（一次切出 4 个 `b-0044`，数据损坏级：划痕/笔记会锚错块）。
- **开发者自己踩的**：一次"无操作"编辑把 `_MAX_GROWTH_RATIO` 注释掉了 →
  所有 `edit_block` 抛 `NameError`，而工具层把异常吞成一句 `工具 edit_block 执行失败` →
  连跑三次都是"0 修订"，看起来像模型不干活。**改完立刻跑 pytest**（该行为已被
  `tests/test_proofread.py` 覆盖；测试没红只是因为改动落在上一次 pytest 之后）。

### ㉝ 补记二（2026-09-15）：`Abstract` 不是标题 —— 解析行级拆分 + agent 补类型工具

## ㉟ 笔记列表 = 按**锚点在原文里的位置**排序（2026-09-15 宿主指示）  `b7c3e9a4`

宿主：「右侧笔记列表，顺序不对。现在看起来好像是最新的笔记在前面。实际上，应该按照笔记
关联的原文的位置为顺序，前面的上面句子的笔记就在上面，下面句子的笔记就在下面。」

### 病灶
`repo.list_notes` 是 `ORDER BY created_at DESC` —— **倒序的写入时间**。这在"边读边记"
的真实用法里必然错位：读第一段时记的笔记，读到第五段再回头看列表，它被挤到了最下面。
（不是"渲染顺序错了"，是查询的排序键选错了。）

### 排序键（`repo._NOTE_ORDER`，服务端唯一事实来源）
1. **有落点的在前**，文献级笔记（`block_id IS NULL`）在后 —— 列表是顺着原文读的，
   没有位置的笔记不该打断中间；块已消失（`b.ord IS NULL`）的同样兜到最后。
2. **`blocks.ord`** —— 阅读顺序，㉜ 分栏感知排好的那个。**不是 `block_id` 的字典序**
   （agent 的 `reorder_page` / ㉜ 会改 `ord` 而不改 id）→ 已留护栏测试。
3. 同一段里：**整段笔记在前**，然后是划住某几个字的。
4. 再按**字符位置**；位置相同时**原文列在前**（与并排阅读的左→右一致）。
5. 最后 `n.id` 兜底 —— 顺序必须**确定**，不因查询计划换位。

### 前端：新增笔记后**重拉列表**，不在前端插位置
`onAdded` 原来是 `setNotes((ns) => [n, ...ns])`（往最前面插），改成重拉 `api.notes()`。
理由同 ㉛ 的「前端不自己包 `<mark>`」：**位置只有服务端算得对**（它才有 `blocks.ord`），
两份排序实现必然分叉。拉不到时兜底追加，绝不把刚写的笔记藏起来。

### 验收
`tests/test_notes_order.py` 6 项（跨块不按写入时间 / 段内按字符偏移 / 整段笔记在本段区间

回退修复 5/6 项转红。真浏览器（真鼠标事件）：倒序创建四条 → 列表按文档位置显示；
再真拖选一段写笔记 → 新笔记落在**中间**（修复前会插到最顶上）。

### ⚠️ 两处"无位置"的默认（宿主未表态，实现时选了其一，一句话可翻转）

## ㊱ 「待读 → 在读」自动翻转 + `last_read_at`（2026-09-15 宿主指示）  `c4e7a1b9`

宿主：「我有篇文章读了 13%，为什么『在读』还是 0 篇？」→ 追到底后问的是
**「那么，什么时候变成 unread 呢？」** → 助手用代码事实回答：

- **导入即 `unread`**（`INSERT` 写死默认值，PDF 上传与 arXiv 导入都一样）；
- **没有任何自动回到 unread 的路径**；`progress` 只增不减（⑰），滚动从不改状态；
- **唯一路径是人手动标回「未读」**（看板拖拽；阅读器里那个按钮只能标「已整理」），
  且会**把进度清零**（否则出现"未读 但 80%"）。

⇒ 于是当时的「待读」实际上等于**「从未被手动标过状态的」**，读 90% 也躺在待读列。
宿主拍板：**「是」**（读过但没读完 = 在读）。

### 确定
| 事实 | 来源 | 是否自动 |
|---|---|---|
| **百分比** | 阅读器滚动上报 | 自动累计（只增不减，⑰ 不变） |
| **待读 → 在读** | 同上（"开始读了"这件事滚动位置是知道的） | ✅ **自动**（本轮新增） |
| **已读 / 已整理** | 手动拖看板 | ❌ 只能手动（"读懂没有"只有人知道，⑰ 保留） |
| **回到待读** | 手动标「未读」 | ❌ 只能手动；进度清零 |

于是「待读」有了明确含义 = **从没读过**（或手动标回未读）。

### 实现要点（都踩过或想清过）
1. **只在翻转那一刻盖 `status_at`**，不能每次滚动都盖 —— 否则它退化成"最近滚动时间"，
   看板列内排序（按 `status_at`）会让正在读的文献在列里乱跳，总览那条"停摆"提醒也读不出停了多久。
2. **新增 `papers.last_read_at`**（"最近阅读"）：**只有滚动上报写它**。
   ⚠️ **不能复用 `updated_at`** —— 那个被任何 PATCH 刷新（改标题/改标签/拖看板都算），
   记的是"最近一次改动"。`paper_public` 加字段 → 登录态与分享态自动同形（⑩）。
3. **「只增不减」的护栏照旧**：进度回退值仍被丢弃，但 `last_read_at` **照记**
   （翻回来也是在读这篇，若这时不刷新，看板会误报成"停摆"）。
4. **手动标记「已读」后进度锁定**：滚动上报被 409 拒 → **不得留下任何阅读痕迹**
   （否则"最近阅读"会在已读的文献上继续跳动，也就不再是阅读信号了）。
5. **迁移**：存量行**只回填有证据的**（`progress > 0`；这类行的 `updated_at` 就是最后一次
   滚动上报的近似），`progress = 0` 的一律留 NULL（不编时间戳）。
6. **文献库「中文版」列**：不再显示"生成时间"（宿主：不需要），改「创建 MM-DD · 最近阅读 X天前/未读」。
   原先那句 `已生成 · N天前` 读的是 `status_at`（**阅读状态**时间戳）却拿来当**生成时间**显示 ——
   自动翻转一上线它就会变成"今天"，属于语义错位；原型那格本来也只有「已生成」两个字。
7. **总览「在读已停摆 21 天」改用 `last_read_at`**（原来用 `status_at`，
   在自动翻转后一个人天天读同一篇也会被报成停摆）。

### 验收
`tests/test_last_read.py` 9 项（导入即待读+无阅读时间 / 滚动翻转 / `status_at` 只盖一次 /
回退只刷新最近阅读 / 手动优先 / 已读锁定不留痕 / **只有滚动能写 last_read_at** /
迁移只回填有证据的 / 分享态与登录态同形）—— 把功能关掉 **6/9 转红**。
真浏览器实测（本地 8012，真实滚动 + 查库取证）：待读 → 滚动 → 看板「在读」+1、
文献库那格变「已生成 · 创建 09-15 · 最近阅读 今天」；重开再滚 `status_at` 不再被盖、
`last_read_at` 前进；**真拖拽**拖回「待读」→ `status=unread` + 进度清零
（真鼠标拖只发 `dragstart/dragover` 不发 `drop`，要 CDP `Input.setInterceptDrags` +
`dispatchDragEvents` 才生效）。

### 拖回「待读」时，`last_read_at` 清不清？（宿主 2026-09-15 选 **B**）

- **A**（助手倾向）连同 `last_read_at` 一起清 → 「待读」严格等于"从没读过"，
  与看板提示「拖回『待读』则清零重来」名实相符；代价是抹掉"确实读过"这个事实。
- **B**（**宿主选定**）**留着** —— 手动标回「未读」只清 `progress` + `progress_mode='auto'`，
  `last_read_at` 不动，那格照旧显示「最近阅读 今天」；「待读」= "我把它放回来了"，事实优先。

⇒ 代码正是 B（`patch_paper` 的 unread 分支不碰 `last_read_at`），**未改任何行为**。

## ㊳ 凡是有可选文字的块都可划：标题与参考文献条目补上坐标系（2026-09-16 宿主指示）  `e6b1c7a2`

| 服务端 | `pipeline/markup.py::render_block` | 标题分支与 `refs` 分支改走 `prose(text)`（原 `_esc(text)`）；新增 `wrap` 参数，`wrap=False` 只回**内部** HTML |

| 前端 | `web/src/pages/Reader.tsx` | `BlockBody` 加 `as='div'\|'span'`；标题分支改 `<span className="b-en"><BlockBody … as="span"/></span>` |

### 三条硬的实现约束（都是被浏览器/规范逼出来的，不是风格选择）

1. **标题的 `<h1..h4>` 外壳只能有一层**：阅读器自己渲 `<h2 class="doc-h lvlN" data-b=…>`
   （挂块 id 与字号层级）。服务端若再套 `<h2 class="sec">` 就得到 `<h2><h2>` ——
   **浏览器会把内层甩到标题外面**（中途真的踩过这一版）。
2. **标题里一律用 `span`，绝不能用 `div`/`p`**：`<h2>` 只允许**短语内容**，
   塞块级元素会被浏览器甩出去（`<p>` 同理 —— 没有 HTML 时的纯文本回落也走 fragment 不走 `<p>`）。
3. **`prose()` 在 `typeset=False` 时逐字等于 `_esc()`**：所以导出 / 校验 / prompt 三条路径
   （`anchors` 默认 False）的产物**一个字节都没变** —— 这点有测试钉住，是本改动敢动的底气。

### 边界（诚实划清）

直接把内嵌字节当装饰图贴出来 → 屏幕上就是**一个光的灰方块**（宿主原话「springer 的图还是没有」，
看起来像"改了没生效"）。修法 = 页边带里的无图注小图**也走整体栅格化**（`_add_graphic`），

   且屏幕上的渲染 = 导出 HTML 的渲染（"保版式"这个卖点的实现前提）。
2. **改块/重译必须回完整块对象**：后端 `PATCH /api/docs/{id}/blocks/{bid}` 与
   `POST .../retranslate` 返回的是**整块公开形状**（含重渲染的 `zh_html`），前端整块替换。
   ⚠️ 踩过：原先只回 `{id, zh}`，前端只能就地改纯文本字段，`zh_html` 停在旧版本 ⇒
   **"保存成功但界面纹丝不动"**（看着像没生效，其实库里已更新）。译文含公式时尤其明显。

### 部署形态（重要，影响路由设计）

后端**同时**当 API 与 SPA 宿主（决策② 单进程），所以：
- 任何未知 GET 落到 SPA 兜底（刷新 `/plans/3`、分享链接都能用）；
- 但**带扩展名的路径必须 404**（旧 hash 的 `/assets/x.js`），否则浏览器把 HTML 当 JS 解析，
  报一堆无关语法错误、掩盖真正的 404；
- 顶层静态小文件（`favicon.svg` 等）走**白名单**路由，不能用通配（否则 `..` 可穿越）。

### 真机验证暴露并修掉的缺陷（全部已修 + 留测试）

> 方法论：**每一处都先在真浏览器里复现、用 DOM/截图取证，再改代码、再回真浏览器确认**。
> 只靠"测试绿"会漏掉第 3/4/6/7 条（它们全是呈现层问题，离线回归根本看不见）。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 无公式论文（零 LLM 块）一律「转换失败」 | `_zh_html(doc)` 签名漏了新增的 `typeset` 参数 → 校验那一步 `TypeError`；**带公式的论文走不到那句**，所以只在"没东西可译"的 PDF 上暴露 | 补签名；并把「零 LLM 论文」列为必测路径 |
| 2 | 未配 LLM 却报「疑似漏译」 | 缺前置检查，整篇一路跑到校验，因为"一个块都没译"而报校验失败 → 用户去查翻译质量 | `_run` 开头 fail fast，报错**点名环境变量**；同时只在 `looks_math` 为真时才调 LaTeX 化（纯文本论文不必碰 LLM） |
| 3 | 进度条会往回退（100% → 3%） | 前端滚动上报是节流的，从文末快速滚回顶部时最后一次上报把进度拽回去 | 后端 **auto 模式进度只增不减**；标回「未读」→ 进度清零（避免"未读 但 80%"） |
| 4 | 重试按钮被"转换失败"挤成两行、失败原因藏在 tooltip | 列宽不足 + 原因只挂 `title` | 转换列加宽、按钮 `nowrap`、**失败原因全文直接显示在行内**（⑪ 要求它可见）|
| 5 | 分享页把所有未就绪文献都写成「转换中」 | 未区分 `failed` | 分开显示「转换失败」；匿名读者看到的 409 文案改成一句人话（原先沿用给登录用户的"稍后自动刷新"）|
| 6 | 状态下拉框把箭头压到字上 | 选择框按当前选项宽度自适应 | 显式宽度 |
| 7 | 手机宽度下文献表被挤成"每行两个字" | 响应式媒体查询写成了 `900em`（= 14400px，**永不触发**） | 改 `900px`；文献表在窄屏**横向滚动**（`.table-scroll`），不硬压 |
