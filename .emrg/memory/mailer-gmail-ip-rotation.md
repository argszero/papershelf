# 发信可靠性：Gmail 的 DNS 池是有偏的，单次尝试必然漏信

**一句话**：`smtp.gmail.com` 解析出的 IP 里有一部分从部署机**连不通**，而 `smtplib`
只解析一次、只连一个地址 —— 所以**必须重试**，否则每 3 次注册就有 1 次收不到验证码。

## 实测数据（2026-09-11，生产部署机 `39.105.53.16`）

24 次全新解析 + 全新连接：

| IP | 被抽中 | 连接失败 |
|---|---|---|
| `173.194.43.108` | 9 | **9（100%）** |
| `142.251.188.109` | 6 | 0 |
| `142.250.107.109` | 5 | 0 |
| `142.250.99.109` | 4 | 0 |

- **单次尝试失败率 = 9/24 = 37.5%**（不是均匀轮转，是**有偏**的：坏 IP 反而被抽得最多）
- 坏段是 `173.194.43.0/24`；`142.250.107.0/24` 也见过一个坏 IP
- 连不通的表现是**超时**（不是 ECONNREFUSED），所以超时值直接决定用户等待时长
- **重试确实有效**：每次重试都是新的 DNS 查询，实测首次超时后第 2 次即成功

## 重试次数怎么定（别拍数）

残留失败率 = `0.375^n`：

| 尝试次数 | 残留失败率 |
|---|---|
| 1 | 37.5% |
| 3 | 5.27% ← 第一版拍的 3 次，实测**每 8 次仍失败 1 次** |
| **5** | **0.74%** ← 采用 |
| 6 | 0.28% |

当前参数：`_TIMEOUT=6s` / `_ATTEMPTS=5` / 退避 `0.4s`。
最坏耗时（连续 5 次都抽中坏 IP，概率 0.7%）≈ 34 秒。
超时给 6 秒而不是 20 秒：Gmail 正常握手 <0.5s，6 秒足够判定"这个 IP 不可达"，
降下来是为了让"抽中坏 IP"的代价小一点。

## 为什么本地测不出来（最该记住的一条）

**两道屏障同时把这一层遮住了**：

1. 本地端到端用的是**假 SMTP 服务器**（`localhost:2525`）—— 不轮转、也没有到 Gmail 的链路。
2. `tests/test_server.py` 的邮件夹具把 `mailer._send`（公共出口）**整个换掉**了 ——
   它只验证"业务在什么时机发信"，**根本不走 SMTP 连接逻辑**。

所以"本地全绿 + 生产两成失败"完全可能。补 `tests/test_mailer.py` 时专门打**被绕过的那一层**
（用"先失败后成功"的假传输层，不需要网络）。

## 通用教训

- **换一个外部服务方（SMTP/CDN/API）就换了一套网络拓扑**；本地/CI 能通不代表部署机能通。
  凡是"依赖外部主机可达性"的功能，本地替身（mock/localhost）都会**系统性地漏掉**这类缺陷。
- **凡是 "抽一个资源、连一个资源" 且有不可达分支的，都要重试**（DNS 轮转、连接池、多副本）。
- 定重试次数要**先测失败率**，再算 `p^n`；凭感觉给 2–3 次很容易不够。
- 失败模式是**静默**的：用户只看到"发送失败，请稍后重试"，日志里只有一条 warning。
  这类"偶发"缺陷必须靠**多次重复实测**才能看见（单次尝试 70% 会成功，跑一次就"通过"了）。
