# 问题⑮ 邮箱验证怎么落地？（SMTP 是部署门槛）—— ⏳ 待宿主作答

**提问时间**：2026-09-10（⑭「开放注册 + 限 `.edu.cn`」归档后立即提问，宿主尚未回答）。

## 为什么必须问
⑭ 的强绑定推论：**不做邮箱验证 → 随手填假的 `xxx@xxx.edu.cn` 即可通过 → 白名单形同虚设**。
故邮箱验证从「可选」升级为「**必需**」，连带引入 **SMTP 配置**（自托管 = 部署者自己提供发信服务）。
自托管开源项目里**强制 SMTP 是真实的部署门槛**（只想自己用/给几个同学用的人被挡住）→ 需宿主定调。

## 选项（已给宿主）
- **A. 强制配置 SMTP** —— 部署时必须配好，注册即发激活邮件，不点链接不能登录
  → 严格无死角；但**想快速起实例的人被挡住**
- **B. SMTP 可选 + 自动降级**（**助手推荐**）——
  - 配了 SMTP → 开放自助注册（`.edu.cn` 白名单 + 邮件激活）
  - 没配 SMTP → **自动关闭开放注册**，退化为「管理员后台开号」
  → 默认安全 + 本地零配置可跑；发信严格性由部署者按需开启
- **C. 不做邮件验证，改管理员审批** —— 注册后进待审队列，管理员点通过
  → 绕开 SMTP；但与 ⑭ 的「开放注册、规模可不止几个人」冲突，审批会成为宿主日常负担
- **D. 只校验域名格式，不验证真实性** —— 最省事，**助手明确不建议**：等于对全网开放烧部署者的 Key（⑧）

## 助手的连带提醒（已在答复中说明）
- ⑭ 的费用滥用面仍不小（`.edu.cn` 覆盖数千所高校）→ **决策⑧ 的成本护栏（并发/单篇 token 预算/重试上限）更要紧**
- 域名白名单应**可配置**（默认 `edu.cn`，部署者可增删/放宽），不硬编码
